## 1. Umgesetzte Owner-P0s

**P0-01 Evidence SSOT:** `.atc/evidence/evidence.yaml` je Repository — maschinenlesbar,
ehrlich nach Statusleiter SPECIFIED→IMPLEMENTED→TESTED→VERIFIED→AUDITED→RELEASED.
Dimensionen: implementation (substantial/partial/skeleton/docs_only), tests
(pass_with_evidence/not_run/not_applicable + Evidence-Referenz), security
(not_audited), conformance (not_verified), release (development),
milestone_claims (M nur mit Evidence-Bundle, ATC-STD-MILESTONE-001).
Reifeklassen A/B/C und R-Level aus dem Owner-Deep-Dive übernommen.
Status-Philosophie verbindlich: CLAIMED ≠ PASS · DOCUMENTED ≠ IMPLEMENTED ·
IMPLEMENTED ≠ VERIFIED.

**P0-02 Canonical Ownership:** `registry/repositories.yaml` mit `capabilities:`
— je Funktion EXAKT EIN kanonisches Repository (language=atclang, kernel=atc-shivacore,
vm_runtime=atc-vm, consensus=atc-algorithm, blockchain_orchestration=a-townchain,
node_runtime=atc-node, contracts=atc-contracts, zkp=atc-zkp, os=globus-os, ai=aurora-ai,
integration=a-townchain-os, standards=atc-standards, architecture_docs=a-townchain-os-docs …).
**Konsens-Regel (F-105):** Konsens-Implementierung liegt KANONISCH bei atc-algorithm;
a-townchain orchestriert nur. Eine zweite Konsens-Implementierung in a-townchain ist
verboten (CI-Kontrolle: Registry-Feld + Review-Gate).

**P0-03 Kein Status-Claim ohne Evidence:** Statusleiter in jeder Evidence-Datei verankert;
atc-contracts-M6-Claim auf CLAIMED zurückgestuft (README-Klarstellung, F-106).
