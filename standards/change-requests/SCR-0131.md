# SCR-0131 — Reconcile canonical capability ownership after SCR-0127

| Feld | Wert |
|---|---|
| SCR-ID | SCR-0131 |
| Datum | 2026-10-11 |
| Auslöser | Cross-repository SSOT review following a-townchain-os-docs PR #43 |
| Typ | GOVERNANCE / REGISTRY-CONSISTENCY |
| Status | PROPOSED — owner decision and §9 approval required |
| Scope | Clarify capability ownership in registry; no protocol or runtime behavior change |

## 1. Problem statement

The current `registry/repositories.yaml` contains two ownership eras that need an explicit, machine-checkable distinction:

- The repository inventory records `atc-vm` and `atc-algorithm` as `frozen`, `canonical: false`, migrated to `a-townchain/components/vm` and `a-townchain/components/algorithm`.
- The `vm_runtime` capability points to `a-townchain` and names `a-townchain/components/vm` as the runtime SSOT, while `vm_specification` points to `atc-vm` with only an owner-nomination note.
- The `consensus` capability points to `a-townchain` and names `a-townchain/components/algorithm` as the implementation location, while `consensus_algorithm` points to frozen `atc-algorithm` without stating whether this means normative specification, governance, or implementation.
- SCR-0080/SCR-0081 contain earlier ownership statements from before the SCR-0127 monorepo migration. Those historical statements must not silently override the later migration record.

This is a semantic ownership ambiguity, not proof that the implementation itself is duplicated. No implementation or standard is declared wrong by this proposal alone.

## 2. Proposed resolution for owner review

Adopt explicit, non-overlapping capability meanings, subject to evidence and owner approval:

| Capability meaning | Proposed authoritative location | Required clarification |
|---|---|---|
| VM runtime implementation | `a-townchain/components/vm` | Registry capability remains `vm_runtime`; source repository `atc-vm` stays frozen/non-canonical |
| VM specification / governance | `atc-vm` only if its approved scope and maintained normative artifacts substantiate this role; otherwise assign to the approved standards authority | Do not infer spec authority from repository name or owner nomination alone |
| Consensus implementation | `a-townchain/components/algorithm` | Enforce one production implementation and preserve F-105 boundary |
| Consensus specification / governance | `atc-algorithm` only if approved scope and normative artifacts substantiate this role; otherwise assign to the approved standards authority | Separate specification ownership from implementation ownership in capability names and validation |

## 3. Required evidence before registry changes

1. Inspect approved standards, SCR-0127 migration evidence, repository metadata and current canonical source paths.
2. Identify normative specification artifacts and their approval status in each candidate repository.
3. Search consumers of `capabilities.vm_specification` and `capabilities.consensus_algorithm` before renaming or changing keys.
4. Define compatibility handling for generated views, validators, profiles and cross-registry checks.
5. Record the accountable owner and obtain required §9 approval before changing normative registry state.
6. Regenerate generated views and run the full standards validation, repository audit, registry consistency and cross-registry gates on the exact commit.

## 4. Non-goals and safety constraints

- Do not change transaction encoding, consensus behavior, VM bytecode, ABI, protocol serialization or kernel boundaries.
- Do not unfreeze, archive, delete or reactivate any repository as part of this SCR.
- Do not change `layer_taxonomy_draft`; it remains DRAFT until ATC-STD-LAYER-001 receives its required approval.
- Do not modify `registry/repositories.yaml` or generated views until the owner decision and applicable approval are recorded.
- Do not mark this SCR APPROVED or VERIFIED based on documentation CI alone.

## 5. Acceptance criteria

- Every capability has one clearly defined semantic meaning and one authoritative owner.
- Specification/governance ownership is distinguishable from production implementation ownership.
- The registry inventory, migration evidence, generated views and validators agree.
- F-105's single-consensus-implementation boundary remains enforced.
- Exact-SHA validation evidence and required owner approval are linked before closure.

## 6. Current disposition

PROPOSED. This document records the discrepancy and a review path; it does not itself authorize a registry change or establish a new normative ownership decision.
