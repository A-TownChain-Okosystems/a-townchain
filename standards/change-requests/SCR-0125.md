# SCR-0125 — Family-Scoped Standard ID & Taxonomy Architecture

| Feld | Wert |
|---|---|
| SCR-ID | SCR-0125 |
| Datum | 2026-09-14 |
| Status | PROPOSED |
| Affected Standards | ATC-STD-000, ATC-STD-002 |
| Scope | Standard-ID, Family, Category, Class, Registry, Generator, Validator, migration |
| Change Type | Governance / Breaking taxonomy evolution |
| Risk | R2 — Registry/tooling migration |

## 1. Decision Requested

Einführung eines kanonischen, Family-scoped Standard-ID-Modells für das
ATC-Standardsystem. Die bestehende globale Nummerierung `ATC-STD-xxx` wird
nicht rückwirkend umdefiniert. Bereits vergebene IDs bleiben immutable und
werden als Legacy-IDs erhalten.

## 2. Target Taxonomy

Die normative Taxonomie lautet:

```text
FAMILY
  ↓
CATEGORY
  ↓
CLASS
  ↓
STANDARD
```

Jeder normative Standard MUSS genau einer Family, Category und Class
zugeordnet sein.

### 2.1 Family

Format: `FNN` — z.B. `F03`.

Eine Family besitzt einen eigenen, unabhängigen Standard-Nummernraum.
Family-IDs sind immutable und dürfen nach Freigabe nicht wiederverwendet
werden.

### 2.2 Category

Format: `CNN` — z.B. `C01`.

Categories werden innerhalb einer Family definiert. Eine Category-ID ist
innerhalb ihrer Family eindeutig.

### 2.3 Class

Format: `CLNN` — z.B. `CL01`.

Classes werden innerhalb einer Category definiert. Eine Class-ID ist
innerhalb ihrer Category eindeutig.

### 2.4 Standard

Kanonisches Format:

```text
ATC-STD-F{family_id}-{sequence}
```

Beispiele:

```text
ATC-STD-F01-001
ATC-STD-F01-002
ATC-STD-F02-001
ATC-STD-F03-001
ATC-STD-F03-002
```

Die Sequenz ist ausschließlich innerhalb der Family eindeutig.

## 3. Canonical Standard Record

```yaml
standard:
  id: ATC-STD-F03-001
  version: 1.0.0
  status: stable
  lifecycle: frozen
  family:
    id: F03
    name: Blockchain
  category:
    id: C01
    name: Identity
  class:
    id: CL01
    name: Chain Identity
  sequence: 1
  title: Chain Identity & Network Identification
  normative: true
  legacy_ids:
    - ATC-STD-600
```

`family_id + sequence` MUSS innerhalb der Registry eindeutig sein.

## 4. Immutability and Allocation

1. Eine Standard-ID wird nach Vergabe niemals wiederverwendet.
2. Eine veröffentlichte Standard-ID bleibt unverändert.
3. Eine Sequenz beginnt je Family bei `001`.
4. Retirement gibt eine Sequenznummer nicht frei.
5. Generatoren dürfen IDs nicht eigenmächtig vergeben oder renummerieren.
6. Die Registry bleibt Allokations-Autorität.
7. Family-, Category- und Class-IDs sind ebenfalls immutable nach Freigabe.
8. Eine Umklassifizierung erfolgt ausschließlich über einen Governance/SCR-
   Prozess; keine stille Mutation bestehender Records.

## 5. Legacy Mapping

Bestehende globale IDs bleiben gültig und erhalten einen expliziten Alias:

```yaml
migration:
  legacy_id: ATC-STD-600
  canonical_id: ATC-STD-F03-001
  migration_status: mapped
  effective_version: 2.0.0
```

Legacy-IDs dürfen niemals gelöscht, recycelt oder einem anderen Standard
zugeordnet werden.

## 6. Blockchain Family Example

Zielhafte Zuordnung:

```text
F03 — Blockchain
  C01 — Identity
    CL01 — Chain Identity
      ATC-STD-F03-001  Chain Identity & Network Identification
      ATC-STD-F03-002  Genesis Specification & Genesis Identity
      ATC-STD-F03-003  Transaction Domain Separation & Replay Protection
      ATC-STD-F03-004  Network Environment Specification
      ATC-STD-F03-005  Protocol & VM Version Compatibility
      ATC-STD-F03-006  Chain Identity Validation
      ATC-STD-F03-007  Chain Identity Registry
```

Diese neuen IDs ersetzen nicht stillschweigend die bereits vergebenen
`ATC-STD-600..607` IDs. Die bestehende Historie wird über das Mapping erhalten.

## 7. Repository Changes Required After Approval

Nach Genehmigung müssen mindestens folgende Komponenten migriert werden:

- `ATC-STD-000` — neue normative ID-/Taxonomie-Regeln
- `ATC-STD-002` — Family-Architektur und Nummernräume
- `registry/families/` — Family SSOT
- `registry/standards/` — kanonische Standard-Records
- Legacy-to-canonical ID mapping registry
- `registry/standards.yaml`
- `registry/framework.yaml`
- `registry/dependencies.yaml`
- `registry/standard-implementation.yaml`
- `INDEX.md`
- Generatoren unter `tools/`
- Naming-/Registry-Schemas
- Validatoren und CI-Gates
- Referenz- und Dependency-Auflösung

Generated artifacts MUST aus derselben autoritativen Taxonomie abgeleitet
werden. Manuelle Teil-Rewrites generierter Dateien sind unzulässig.

## 8. Compatibility Strategy

Die Migration erfolgt in zwei Phasen:

### Phase A — Dual Namespace

- Legacy-ID bleibt autoritativ für bestehende Standards.
- Neue Standards erhalten Family-scoped IDs.
- Validatoren akzeptieren beide Formate.
- Mapping ist verpflichtend, sobald ein Legacy-Standard migriert wird.

### Phase B — Canonical Family Namespace

- Family-scoped IDs werden kanonischer Identifier für neue und migrierte
  Standards.
- Legacy-ID bleibt als immutable alias erhalten.
- Keine rückwirkende Löschung historischer IDs.

## 9. Validation Requirements

CI/Validator MUSS mindestens prüfen:

- gültiges Family-Format
- gültiges Category-Format
- gültiges Class-Format
- gültiges Standard-ID-Format
- `family_id + sequence` Eindeutigkeit
- Category-Zugehörigkeit zur Family
- Class-Zugehörigkeit zur Category
- Legacy-ID-Eindeutigkeit
- Legacy→canonical Mapping-Eindeutigkeit
- keine Sequenz-Wiederverwendung
- keine stille ID-Mutation
- keine ungültigen Cross-Family-Referenzen
- Generator/Registry-Konsistenz

Fail-closed: Bei einem Verstoß darf der Registry-/Taxonomie-Gate nicht
passieren.

## 10. Non-Goals

Dieser SCR ändert nicht:

- bestehende veröffentlichte Standardinhalte
- bestehende Versionen
- historische IDs
- SCR-IDs
- Requirement-/Test-/Gate-Namespaces
- die normative Immutabilität bereits freigegebener Standards

## 11. Acceptance Criteria

Der SCR gilt technisch als implementiert, wenn:

1. die Taxonomie maschinenlesbar definiert ist;
2. Family-scoped IDs validiert werden;
3. Legacy-Mappings eindeutig validiert werden;
4. Generator und Registry dieselbe SSOT verwenden;
5. bestehende IDs unverändert bleiben;
6. `ATC-STD-F03-001..007` ohne Kollision modelliert werden können;
7. CI bei Duplicate/Mutation/Invalid-Taxonomy fail-closed stoppt;
8. alle generierten Artefakte konsistent regeneriert werden;
9. ein Audit-Evidence-Record die Migration belegt.

## 12. Governance Note

ATC-STD-000 v1.3.0 und ATC-STD-002 v1.0.0 bleiben auf dem bestehenden
Branch unverändert. Dieser SCR ist die formale Änderungsgrundlage für eine
spätere normative Major-Revision und verhindert eine stille Änderung bereits
APPROVED/frozen Governance-Artefakte.
