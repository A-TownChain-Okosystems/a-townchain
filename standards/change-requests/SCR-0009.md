## 1. Antrag

Eigener verbindlicher Versionierungs-Standard für das gesamte Ökosystem: nicht nur Software,
sondern auch Standards, APIs, Smart Contracts, Protokolle, Dokumentation und Releases werden
eindeutig versioniert. Der Owner-Entwurf definiert (23 Abschnitte):

- Semantic Versioning 2.0.0 als Primärstandard (MAJOR/MINOR/PATCH mit Beispielen je Ebene)
- Pre-Release-Kette (alpha → beta → rc → stable)
- Entwicklungsstatus-Katalog (DRAFT/ALPHA/BETA/RC/STABLE/DEPRECATED/EOL), unabhängig von der Version
- Getrennte Ebenen: Software / API / Protokoll / Konsens / State / Network / Contracts / Agents / Doku
- Git-Tags als unveränderliche Release-Referenz; kanonische Versionsquelle (VERSION-Datei)
- Release-ID, Build-ID, Release-Manifest (maschinenlesbar)
- Commit-Versionierung: keine SemVer auf Commits
- Monorepo-Regel (Variante A/B, Vorzug B)
- Versionskompatibilitäts-Deklaration (requires)
- Verbotene Praktiken (latest, final, 1.0 …)
- Golden Rule: Einmaligkeit und eindeutige Zuordnung jeder veröffentlichten Version
- Durchgängige Kette: Requirement → Standard → SCR → Code → Commit → Build → Test → Audit → Release → Tag → Version → Deployment

## 3. Harmonisierungs-Entscheidungen (Standards Governance)

1. **releaseId-Dualformat:** Der Owner-Entwurf nutzt datumsbasierte Release-IDs
   (ATC-REL-20260907-001), das Schema kannte nur versionsbasierte (ATC-REL-1.4.0).
   Lösung: Schema-Pattern erweitert auf beide Formate; je Repository ist konsistent
   EIN Format zu verwenden (REQ-VERSION-015).
2. **Entwicklungsstatus:** Der 7-Status-Katalog (inkl. ALPHA, BETA, RC, EOL) gilt für
   Software-Releases und Release-Manifeste. Für ATC-Standards im engeren Sinne bleibt
   der Lifecycle aus ATC-STD-000 §10 maßgeblich (REQ-VERSION-006 stellt das klar).
3. **Pre-Release-Identifier:** Kanonische Registry-/Standard-Versionen bleiben
   Kern-SemVer `X.Y.Z` (schema versionPatterns.semver, S-03); Pre-Release-Identifier
   (1.0.0-rc.1) sind für Software-Releases und Git-Tags zulässig.
4. **buildId:** Neues Pattern ATC-BUILD-NNN allockiert (nicht im Owner-Entwurf als
   formale ID vorgesehen, aber für Auditierbarkeit von Builds sinnvoll und konsistent).
5. **Verknüpfung mit ATC-STD-CHANGELOG-001 / RELEASE-001 / GIT-001 / AUDIT-001:** Diese
   Standards existieren NOCH NICHT. Sie sind als geplante Folge-Standrote im Standard
   (INFORMATIVE Referenzen) dokumentiert und bedürfen jeweils eigener SCRs + ID-Allokation.
