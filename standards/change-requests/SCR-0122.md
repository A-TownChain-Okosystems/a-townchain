## Inhalt

### 1. Antrag

Festlegung des **Network Release Lifecycle** als verbindliches Reifestufenmodell:

- **Zwei orthogonale Dimensionen:** NETWORK = DEVNET|TESTNET|MAINNET; MATURITY = ALPHA|BETA|STABLE (+ RELEASE CANDIDATE als Gate-Zustand). Die Versionierung allein bestimmt nicht den Netzwerkstatus.
- **Reifestufen-Matrix:** Alpha/Beta NIE produktionsfaehig (auch nicht auf Testnet); nur Mainnet STABLE ist produktionsfaehig.
- **Versionslogik:** 0.x.0-alpha.N / -beta.N auf Devnet/Testnet; >= 1.0.0 nur Mainnet STABLE; Rueckstufungen verboten.
- **6 Release Gates (fail-closed, nie automatisch, nie uebersprungen):** GATE-DEV-ALPHA, GATE-DEV-BETA, GATE-TEST-ALPHA, GATE-TEST-BETA, GATE-MAINNET-RC, GATE-MAINNET-STABLE — jeweils mit Mindest-Eintrittskriterien (Architektur, Belastungstests, Security-Audit, Kompatibilitaet, Recovery, Rollback, Governance-Freigabe, Maintenance Readiness).

### 2. Abgrenzung (keine Duplikate)

- **NET-004 (APPROVED) bleibt SSOT** der Promotion-Pipeline DEVELOPMENT -> DEVNET (GATE-011) -> TESTNET (GATE-012) -> RC -> MAINNET (GATE-013). NET-009 definiert die MATURITY-Dimension INNERHALB der Umgebungen plus Versionssemantik und verdrahtet die Gate-Kriterien mit NET-001..008. Keine Anforderung von NET-004 wird geschwaecht.
- VERSION-001 (Software-SemVer), NET-006 (Upgrades), NET-007 (Security), NET-008 (Recovery), COMPAT-001 unberuehrt.
- Maschinenlesbarer Release State: Erweiterung von registry/networks.yaml um maturity/version-Felder; Evidence-Records nach MAINT-019-Schema (PR #25).

### 3. Ehrlicher Ist-Zustand

Alle drei Netzwerke status=planned (keine Genesis); maturity/version-Felder fehlen in registry/networks.yaml noch — SPECIFICATION_ONLY, CLAIMED != PASS.

### 4. Konsistenz

NET-004 REQ-NET-031 (keine Stufenuebersprünge) wird durch REQ-NET-082 konsistent erweitert; GSEPF/MAINT-Governance (Release-Gates, Evidence) und ATC-STD-203 Release-Gates werden referenziert, nicht veraendert.
